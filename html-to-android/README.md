# html-to-android

Figma 디자인 노드(또는 HTML/CSS/JS 프로토타입)를 관용적인 Jetpack Compose 코드로 변환하는 Claude 스킬. Figma MCP를 실제로 써본 경험에서 출발해, 추측이 아니라 실제 툴 호출과 실제 디자인 파일로 하나씩 확인하면서 만들었다. **판단 단계까지만 확인했고 컴파일·렌더는 아직 안 했다**는 점은 아래 [검증 수준](#검증-수준)에 따로 적었다.

## 상황

여러 Android 프로젝트(자동차, 헬스케어, 개인 포트폴리오 등)를 동시에 진행하면서, Figma 시안을 Compose 화면으로 옮기는 작업이 반복적으로 발생했다. Figma MCP(`get_design_context` 등)를 코딩 에이전트에 연결해서 쓰고 있었는데, 화면을 구현하다 보면 **에이전트가 디자인에 없는 기능을 추론해서 만들어버리는 문제**가 자주 나타났다.

처음엔 "에이전트의 토큰 사용을 아끼는 공용 스킬을 만들자"는 좀 더 넓은 아이디어에서 시작했다(코딩 에이전트 전반의 토큰 절약, 사용량 트래킹, Figma MCP 개선 세 방향을 저울질함). 이 중 실제 개발 생산성에 가장 직접적이고 여러 프로젝트에 반복적으로 쓰이는 게 Figma → Compose 변환이라 이쪽으로 좁혔다.

## 문제

"할루시네이션(기능 추론)이 왜 발생하는가"를 짐작으로 넘기지 않고, 실제 Figma 파일에 직접 도구를 호출해서 원인을 확인했다.

- **1차 원인**: 문제가 있던 요청은 화면 하나가 아니라 **페이지/캔버스 전체 노드**(971개 프레임, 1050개 인스턴스)를 통째로 넘기고 있었다. 범위가 넓으니 에이전트가 뭘 봐야 할지 스스로 판단해야 했고, 그 과정에서 추론이 끼어들었다.
- 한 단계 더 파고들었다: Figma의 공식 `get_design_context` 도구는 섹션/캔버스 레벨 노드에 대해 **코드 생성을 거부하고 하위 노드로 내려가라고 강제**하는 가드가 이미 내장돼 있었다(`forceCode: true`로도 못 뚫음 — 실제로 테스트해서 확인). 즉 "노드를 작은 조각으로 나눠 인식시키는" 기능 자체는 이미 존재했다.
- 그렇다면 뭘 새로 만들어야 하는가? Figma 공식 가이드(`figma-design-to-code` 스킬 리소스)를 직접 읽어보니, 스크린샷 검증·병렬 배치 드릴다운·컴포넌트 재사용·에셋 처리까지 상당 부분이 이미 정의돼 있었다. **진짜 빈 자리는 "Tailwind/CSS 스타일 결과물을 관용적인 Compose 레이아웃으로 옮기는 규칙"** 이었다.

## 사고 과정

새로 만들기 전에 매번 "이미 있는 건 아닌가"부터 확인했다.

1. **디자인 토큰 이원화 아이디어 검토**: "고정 수치(패딩 16, 라운드 10 등)는 LLM에 매번 안 줘도 되지 않나, 매핑 파일로 분리하면 되지 않나"는 제안이 있었다. `get_variable_defs`를 호출해 확인해보니 Figma Variables 메커니즘은 이미 존재했다. 다만 검증한 디자인 파일에는 색상·타이포만 Variable이고 spacing/radius/아이콘 크기는 raw 숫자였다 — 이 최적화는 **코딩 에이전트 쪽이 아니라 디자인 시스템의 성숙도**에 달려있다는 걸 확인하고 스코프에서 뺐다.
2. **기존 도구 조사**: `exfig`(색상/타이포/아이콘/이미지를 Figma에서 각 플랫폼 리소스로 export, Compose Code Connect 생성까지 지원하는 CLI + Claude Code 플러그인)를 발견하고, 이 영역은 직접 만들지 않고 위임하기로 했다. `winson-AI/CodeAgent-exp`도 참고 대상으로 확인.
3. **문제의 보편성 확인**: Figma 공식 포럼에서 "auto-layout 없는 디자인은 구조를 인식할 수 없다"는 같은 불만이 여러 AI 도구 사용자에게서 제기되고 있음을 확인했다. 업계도 못 푼 문제라는 뜻이라 여기에 집중하기로 했다.
4. **범위를 좁힌 뒤 실제 노드로 테스트** (표를 채웠다고 끝내지 않고 세 번 돌려봤다):
   - 바텀시트 노드: **OS가 그려주는 가상 키보드 목업**이 실제 마크업으로 통째로 딸려왔다. 그대로 옮기면 존재하지 않을 가짜 키보드를 구현하게 된다.
   - 리스트 노드: **반복 카드가 템플릿이 아니라 복제된 마크업**으로 왔다. 그대로 옮기면 `LazyColumn` 대신 고정 개수 카드를 하드코딩한다.
   - 홈 화면(360×800): 상태바 목업과 그것이 남기는 inset, 화면 전체가 `absolute top-[N]`으로 배치된 구조(→ 위치 차이로 간격을 계산한 `Column`), 가장자리 고정 헤더/하단 내비(→ `Scaffold` 슬롯), 반복 형제의 컨테이너 선택(가로 4개는 `LazyColumn`이 아니라 `Row`), raw hex를 스타일 목록으로 역조회해 토큰으로 치환하는 방식, SVG → VectorDrawable을 확인했다. 페이지 루트 URL이면 `get_metadata`가 전체 트리를 컨텍스트에 쏟아내므로, 화면 링크를 먼저 요청하도록 했다.
   - 모두 실제 출력을 근거로 규칙표에 추가했다.
5. **HTML 입력 경로 보강**: 실제 HTML은 HTML + CSS + JS가 합쳐진 결과라, JS가 토글하는 클래스를 상태 변형으로 추적하고 JS가 생성하는 DOM까지 읽도록 했다. 대신 컨텍스트 폭증이 재발하지 않게 읽는 파일을 대상 화면의 셀렉터와 관련된 것으로 한정했다.
6. **시각 검증 단계 추가**: Figma는 기준 스크린샷을 이미 자동으로 주지만 HTML 입력은 기준이 없고, Compose 결과를 렌더해 비교하는 단계도 없었다. PixelRAG(렌더러와 스킬 정의)를 소스까지 읽고 **방식만** 참고했다(이미지 크기 규칙, crop 비교, 캡처 완전성 확인, network idle 대기, 도구 유무 확인). 코드나 의존성은 가져오지 않았다. 그 렌더러는 모바일 에뮬레이션이 없고 클릭을 못 해서 상태별 캡처에는 쓸 수 없다는 것도 소스에서 확인했다. 핵심 규칙은 "기준 또는 결과 이미지가 없으면 '시각 검증 안 함'이라고 쓰고, 코드만 읽고 충실도를 주장하지 않는다"이다.
7. **틀린 것을 정정**: 그림자를 "`Modifier.shadow`로는 근사만 된다"고 적었다가, 공식 문서를 확인하니 `Modifier.dropShadow`/`innerShadow`가 있어 그 기준으로 고쳤다. 확인 없이 단정한 게 원인이었고, 이력은 changelog에 남겼다.
8. **토큰 효율화**: 스킬은 트리거될 때마다 본문이 통째로 로드되므로, 테스트 이력은 `references/changelog.md`로, 도구가 있을 때만 필요한 캡처 절차는 `references/visual-verify.md`로 분리했다. 필요하다고 검증된 적 없는 자명한 규칙(`padding`/`gap` 등)은 삭제했다. 현재 `SKILL.md`는 약 8.5KB다.

## 결과

```
html-to-android/
├── SKILL.md                  # 영어, 트리거 및 실행 로직 (매번 로드됨)
├── SKILL.ko.md               # 한글, 사람이 읽는 참고본 (자동 로드 안 됨)
└── references/
    ├── visual-verify.md      # 캡처 감지/명령어/비교 방법 (캡처할 때만 읽음)
    ├── visual-verify.ko.md
    ├── changelog.md          # 발견/변경 이력
    └── changelog.ko.md
```

**하는 일**: Figma 노드 URL 또는 HTML/CSS/JS 프로토타입을 입력받아 —
1. Figma의 노드 청킹 규칙을 정확히 따른다(섹션/캔버스에서 억지로 코드를 뽑지 않고, 페이지 루트면 화면 링크부터 요청).
2. HTML이면 HTML↔CSS↔JS 연결을 표로 정리하고, 짝이 안 맞는 항목은 추론하지 않고 open question으로 남긴다.
3. 프로젝트의 디자인 토큰을 조회해서 쓰고, 없으면 지어내지 않고 표시한다.
4. 절대좌표/Tailwind 마크업을 Compose 관용구로 옮긴다. OS 목업, 반복 리스트, 화면 단위 절대 배치, 그림자 같은 문자 그대로 옮기면 안 되는 패턴을 식별한다.
5. 가능하면 기준/결과 스크린샷을 같은 배율로 잘라 비교하고, 못 했으면 못 했다고 쓴다.

**의도적으로 안 하는 일**:
- 색상/타이포/아이콘 리소스 동기화 — `exfig` 같은 별도 도구에 위임
- 상태 관리, ViewModel 연결, 네비게이션, 데이터 fetch — 결과물은 레이아웃, 스타일, 시각 상태 변형까지

## 검증 수준

- **Figma 경로**: 실제 노드 3건(바텀시트, 리스트, 홈 화면)을 조회해서 규칙에 비춰 **변환 결정이 어떻게 갈리는지**까지 확인했다. Compose 코드를 컴파일하거나 렌더해 본 적은 없다.
- **HTML 경로, 시각 검증 캡처 흐름**: 실제로 돌려보지 않았다.
- **"스킬이 있어서 더 나아졌다"는 측정되지 않았다.** 스킬 없이 돌린 독립 실행이 없어서, 지금까지의 비교는 "문자 그대로 옮기면 이렇게 된다"는 가정과의 비교다. 진짜 A/B는 같은 화면을 스킬 있음/없음으로 각각 변환해서 남은 하드코딩 값, 중복 블록, 목업 구현 여부, 임시 URL 잔존, crop 비교로 보면 된다.
- 문서에서 확인하지 못한 것: `Modifier.dropShadow`의 최소 Compose 버전, CSS blur와 `Shadow.radius`의 동등성. 규칙에는 "확인하라"고 적어 두었다.

## 사전 조건

- Claude에 Figma MCP 커넥터 연결
- (선택) 디자인 토큰/에셋 자동 동기화가 필요하면 [`exfig-plugins`](https://github.com/DesignPipe/exfig-plugins)
- (선택) 시각 검증: HTML 기준 캡처용 렌더 도구(pixelshot, Playwright, headless Chrome 중 하나), Compose 결과 캡처용으로 프로젝트에 이미 설정된 Roborazzi / Paparazzi / Compose Preview Screenshot Testing 또는 에뮬레이터. 없으면 스킬이 "시각 검증 안 함"이라고 보고하며, 빌드 파일 수정이나 설치는 묻지 않고 하지 않는다.

## 기여

실제 화면을 변환하다가 이 스킬이 커버 못 하는 패턴을 발견하면, `SKILL.md`의 4단계 표와 `references/changelog.md`에(영어/한글 두 버전 모두) 근거가 된 실제 출력과 함께 추가해서 PR로 올려주면 된다. 규칙을 지울 때도 같은 방식으로, 실제 변환에서 문제가 없었다는 근거를 남긴다.
