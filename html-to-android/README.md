# html-to-android

Figma 디자인 노드(또는 HTML/CSS 프로토타입)를 관용적인 Jetpack Compose 코드로 변환하는 Claude 스킬. Figma MCP를 실제로 써본 경험에서 출발해, 추측이 아니라 실제 툴 호출과 실제 디자인 파일로 하나씩 검증하면서 만들었다.

## 상황

여러 Android 프로젝트(자동차, 헬스케어, 개인 포트폴리오 등)를 동시에 진행하면서, Figma 시안을 Compose 화면으로 옮기는 작업이 반복적으로 발생했다. Figma MCP(`get_design_context` 등)를 코딩 에이전트에 연결해서 쓰고 있었는데, 화면을 구현하다 보면 **에이전트가 디자인에 없는 기능을 추론해서 만들어버리는 문제**가 자주 나타났다.

처음엔 "에이전트의 토큰 사용을 아끼는 공용 스킬을 만들자"는 좀 더 넓은 아이디어에서 시작했다(코딩 에이전트 전반의 토큰 절약, 사용량 트래킹, Figma MCP 개선 세 방향을 저울질함). 이 중 실제 개발 생산성에 가장 직접적으로 도움이 되고, 회사/사이드 프로젝트 전반에 반복적으로 쓰이는 게 Figma → Compose 변환이라 이쪽으로 좁혔다.

## 문제

"할루시네이션(기능 추론)이 왜 발생하는가"를 짐작으로 넘기지 않고, 실제 Figma 파일에 직접 도구를 호출해서 원인을 확인했다.

- **1차 원인**: 문제가 있던 요청은 화면 하나가 아니라 **페이지/캔버스 전체 노드**(971개 프레임, 1050개 인스턴스)를 통째로 넘기고 있었다. 범위가 넓으니 에이전트가 뭘 봐야 할지 스스로 판단해야 했고, 그 판단 과정에서 추론이 끼어들었다.
- 여기서 멈추지 않고 한 단계 더 파고들었다: Figma의 공식 `get_design_context` 도구는 섹션/캔버스 레벨 노드에 대해 **코드 생성을 거부하고 하위 노드로 내려가라고 강제**하는 가드가 이미 내장돼 있었다(`forceCode: true`로도 못 뚫음 — 실제로 테스트해서 확인). 즉 "노드를 작은 조각으로 나눠 인식시키는" 기능 자체는 이미 존재했다.
- 그렇다면 뭘 새로 만들어야 하는가? Figma 공식 가이드(`figma-design-to-code` 스킬 리소스)를 직접 읽어보니, 스크린샷 검증·병렬 배치 드릴다운·컴포넌트 재사용·에셋 처리·검증까지 상당 부분이 이미 정의돼 있었다. **진짜 빈 자리는 "Tailwind/CSS 스타일 결과물을 관용적인 Compose 레이아웃으로 옮기는 규칙"** 하나였다.

## 사고 과정

새로 만들기 전에 매번 "이미 있는 건 아닌가"부터 확인했다.

1. **디자인 토큰 이원화 아이디어 검토**: "고정 수치(패딩 16, 라운드 10 등)는 LLM에 매번 안 줘도 되지 않나, 매핑 파일로 분리하면 되지 않나"는 제안이 있었다. 실제로 `get_variable_defs`를 호출해서 확인해보니, 이 아이디어를 뒷받침하는 Figma Variables 메커니즘은 이미 존재했다. 다만 실제 검증한 디자인 파일에는 색상·타이포만 Variable로 관리되고 있었고 spacing/radius/아이콘 크기는 raw 숫자였다 — 즉 이 최적화는 **코딩 에이전트 쪽이 아니라 디자인 시스템의 성숙도**에 달려있다는 걸 확인하고, 스코프에서 뺐다.
2. **기존 도구 조사**: `exfig`(색상/타이포/아이콘/이미지를 Figma에서 iOS/Android/Flutter/Web으로 자동 export, Compose Code Connect 생성까지 지원하는 활발히 유지보수되는 CLI + Claude Code 플러그인)를 발견하고, 이 영역을 직접 만들지 않고 채택하기로 했다. `winson-AI/CodeAgent-exp`(Figma→Compose 변환을 시도하는 오픈소스)도 참고 대상으로 확인.
3. **문제의 보편성 확인**: 이게 이 프로젝트만의 문제인지 아니면 업계 전반의 문제인지 Figma 공식 포럼을 검색해서 확인했다. "auto-layout 없는 디자인은 구조를 인식할 수 없다"는 동일한 불만이 이미 여러 AI 도구 사용자들 사이에서 제기되고 있었다 — 아직 업계도 못 푼 문제라는 뜻이고, 그만큼 여기 집중하는 게 가치 있다고 판단했다.
4. **범위를 좁힌 뒤 실제로 테스트**: 표를 다 채웠다고 끝난 게 아니라, 실제 Figma 노드 두 개(바텀시트, 리스트 화면)에 직접 스킬을 걸어봤다.
   - 바텀시트 노드에서 **OS가 자동으로 그려주는 가상 키보드 목업**이 실제 마크업으로 통째로 딸려온다는 걸 확인 — 규칙 없이 그대로 옮기면 존재하지도 않을 가짜 키보드를 구현하게 된다.
   - 리스트 노드에서 **반복되는 카드가 템플릿이 아니라 완전히 복제된 마크업**으로 온다는 걸 확인 — 규칙 없이 그대로 옮기면 `LazyColumn` 대신 고정 개수 카드를 하드코딩하게 된다.
   - 둘 다 실제 실패 사례를 근거로 규칙표에 추가했다.
5. **토큰 효율화**: 스킬은 트리거될 때마다 전체가 로드되므로, 테스트 이력처럼 실행에 필요 없는 서술은 `references/changelog.md`로 분리했다. 본문 크기가 약 31% 줄었다.

## 결과

```
html-to-android/
├── SKILL.md              # 영어, 트리거 및 실행 로직 (매번 로드됨)
├── SKILL.ko.md           # 한글, 사람이 읽는 참고본 (자동 로드 안 됨)
└── references/
    ├── changelog.md      # 검증/발견 이력 (영어)
    └── changelog.ko.md   # 검증/발견 이력 (한글)
```

**하는 일**: Figma 노드 URL 또는 HTML/CSS 프로토타입을 입력받아 —
1. Figma 자체의 노드 청킹 규칙을 정확히 따르고(섹션/캔버스 레벨에서 강제로 코드를 뽑으려 하지 않음)
2. 프로젝트에 이미 있는 디자인 토큰(색상/타이포)을 조회해서 재사용하고, 없으면 조용히 지어내지 않고 표시하고
3. Tailwind/절대좌표 마크업을 Compose 관용구(Arrangement, Modifier.align, RoundedCornerShape 등)로 정확히 옮기고
4. OS 목업이나 반복 리스트처럼 문자 그대로 옮기면 안 되는 패턴을 식별해서 올바른 형태로 변환한다.

**의도적으로 안 하는 일**:
- 색상/타이포/아이콘 리소스 동기화 — `exfig` 같은 별도 도구에 위임
- 상태 관리, ViewModel 연결, 네비게이션, 비즈니스 로직 — 결과물은 정적 UI 스캐폴딩까지만

**현재 상태**: v1, 실제 화면 2건으로 검증. 실사용 중 새로운 패턴이 계속 나올 걸로 예상되며, 발견되는 대로 `references/changelog.md`와 4단계 규칙표에 반영하는 방식으로 키워나갈 계획이다.

## 사전 조건

- Claude에 Figma MCP 커넥터 연결
- (선택) 프로젝트에 디자인 토큰 자동 동기화가 필요하면 [`exfig-plugins`](https://github.com/DesignPipe/exfig-plugins) 설치

## 기여

실제 화면을 변환하다가 이 스킬이 커버 못 하는 패턴을 발견하면, 4단계 표와 `references/changelog.md` 양쪽에(영어/한글 두 버전 모두) 추가해서 PR로 올려주면 된다.
